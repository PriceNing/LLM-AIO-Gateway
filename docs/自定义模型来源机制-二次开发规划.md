# 自定义模型来源机制 — 二次开发规划

> 日期：2026-08-26 ｜ 作者：jinnnyang ｜ 仓库：`jinnnyang/LLM-AIO-Gateway`（fork）
> 背景：对 LLM-AIO-Gateway 二次开发，解决「隐藏模型无法通过 UI 手动添加、刷新会误删」的问题。

## 1. 现状分析（代码已核实）

### 1.1 模型存储结构
模型全部存在 SQLite `provider_models` 表，与 provider 强关联：

```sql
CREATE TABLE provider_models (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    provider_id TEXT NOT NULL,
    model_id TEXT NOT NULL,
    model_name TEXT NOT NULL DEFAULT '',
    enabled INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL DEFAULT '',
    preprocessor TEXT NOT NULL DEFAULT '',
    image_generation TEXT NOT NULL DEFAULT '',
    responses_status TEXT NOT NULL DEFAULT 'unknown',
    responses_checked_at TEXT NOT NULL DEFAULT '',
    responses_expires_at TEXT NOT NULL DEFAULT '',
    responses_streaming INTEGER NOT NULL DEFAULT 0,
    responses_streaming_status TEXT NOT NULL DEFAULT 'unknown',
    responses_tool_types TEXT NOT NULL DEFAULT '[]',
    responses_error TEXT NOT NULL DEFAULT '',
    FOREIGN KEY (provider_id) REFERENCES providers(id) ON DELETE CASCADE,
    UNIQUE(provider_id, model_id)
);
```

- `ON DELETE CASCADE`：删除 provider → 该 provider 下所有模型（auto + manual）级联删除。✅ 满足需求「供应商删除则自定义模型一起删」。

### 1.2 模型写入途径
| 途径 | 代码位置 | 行为 |
|---|---|---|
| **刷新**（自动发现） | `app/services/discovery.py` `refresh_provider_models` | 调上游 `/v1/models`，新增/更新/删除模型 |
| **新增 provider** | `app/database.py` `add_provider` | `INSERT INTO provider_models`（带 models 数组） |
| **更新 provider** | `app/database.py` `update_provider` | models **合并/插入**（已有 UPDATE，没有 INSERT OR IGNORE，不删） |
| **Admin API** | `PUT /admin/providers/{id}`（`ProviderUpdate.models`） | 后端支持传 models，但 **前端 UI 未暴露** |

### 1.3 ⚠️ 刷新会误删隐藏模型（核心痛点）
`refresh_provider_models` 的删除逻辑：

```python
stale_ids = existing_ids - discovered_ids
if stale_ids:
    db.executemany("DELETE FROM provider_models WHERE provider_id = ? AND model_id = ?",
                   [(provider_id, m) for m in stale_ids])
```

**效果**：刷新 = 与上游 `/v1/models` 完全对齐。任何「上游没在 /v1/models 返回的模型」（隐藏/内测/别名模型）都会被删掉。

**结论**：隐藏模型不能走刷新；手动加的模型一旦刷新就会被清掉。

## 2. 需求（用户原话梳理）

1. **供应商卡片加「添加自定义模型」入口**（UI）。
2. **`provider_models` 表加「来源」字段**，区分 `auto`（自动拉取）/ `manual`（自定义添加）。
3. **刷新只刷自动拉取的模型**；**不删除「自己添加且供应商仍存在」的模型**。
4. **供应商被删 → 自定义模型和拉取模型一起删**（现有 `ON DELETE CASCADE` 已满足）。

### 2.1 语义定案（2026-08-26 子智能体评审后确认）

> 以下三条是评审暴露的模糊点，已定案，开发必须遵守：

1. **`add_provider` 带入的 models = 手动种子 → `source='manual'`**。
   DB 列 `DEFAULT 'auto'` 只针对**刷新自动插入**的行，不代表 add_provider 语义。
2. **`update_provider` 不翻转已有 auto 模型的 source**。自动发现的模型不该只因被编辑过就不再随刷新删除；UPDATE 分支保持 source 不变，仅插入新模型时写 manual。
3. **新增「删除单模型」入口**（`delete_provider_model` + admin DELETE 端点），否则 manual 模型加上后永久卡住。manual 与 auto 模型均可单独删除。

### 2.2 评审发现的额外实现要求

- **`_model_from_row` 必须返回 `source`**（`database.py:1175`），否则 `get_provider`/`get_providers` 返回的 model dict 无 source 键，前端读不到 manual 标记，测试全 KeyError。
- **`add_provider` 返回 dict 也要带 source**（`database.py:1429`），前端据此渲染。
- **刷新 UPDATE 分支要限 `source='auto'`**：`refresh_provider_models` 的 UPDATE 若对 manual 模型执行会覆盖其 model_name（同 id 冲突时状态不一致）。

## 3. 改动方案

### 3.1 数据库：加 source 字段 + 迁移
`app/database.py`：
- `_SCHEMA` 的 `provider_models` CREATE TABLE **加上** `source TEXT NOT NULL DEFAULT 'auto'`。
- 新增迁移函数 `_migrate_provider_models_source(conn)`：PRAGMA 检查列，缺则 `ALTER TABLE provider_models ADD COLUMN source TEXT NOT NULL DEFAULT 'auto'`。
- 在 `init_db` 迁移链里调用（老库升级路径）。
- 存量行自动归 `auto`（迁移默认值）。

### 3.2 刷新逻辑：只删 auto，且不覆盖 manual
`app/services/discovery.py` `refresh_provider_models`：
- `stale_ids` 只对 `source='auto'` 的模型删除；manual 保留。
- **UPDATE 分支加 `AND source='auto'`**：manual 模型即使 id 出现在上游，也不被覆盖 model_name。
- INSERT 分支补 `INSERT OR IGNORE` 防并发 UNIQUE 冲突。
- 空 discovered（上游返回空/异常）→ 保留全部（现有 `if discovered:` 守卫，保持）。

### 3.3 手动添加/删除：写 manual + 删除端点
- `add_provider` / `update_provider`：插入模型时 `source='manual'`；UPDATE 已有模型不改 source。
- `_model_from_row` / `add_provider` 返回 dict：补 `source` 键。
- 新增 `delete_provider_model(provider_id, model_id) -> bool`（`database.py`）。
- 新增 admin 端点 `DELETE /admin/providers/{provider_id}/models/{model_id}`。
- `ModelInfo` 加 `source` 字段（可选）；**注意放宽 id pattern**（评审 1g：真实隐藏模型 id 可能含 `/`、`:`、空格，`^[a-zA-Z0-9._-]+$` 过严）。

### 3.4 前端：供应商卡片加「添加自定义模型」+「转手动」开关
`app/web/static/app.js`：
- 供应商卡片加「添加自定义模型」按钮 → 弹窗输入 `model_id`（+可选 model_name/enabled）。
- 调用 `PUT /admin/providers/{id}` 带 `{"models": [{id, name, enabled}]}`（后端写 manual）。
- 模型管理页给 manual 模型打标（「自定义」徽标），并提示「自定义模型不会随刷新移除」。
- 模型卡片加「删除」按钮 → 调 `DELETE /admin/providers/{id}/models/{model_id}`。

### 3.5 「转为手动」开关（2026-08-26 用户补充，排入本分支）

**背景**：自动发现的模型（source=auto）若用户在 UI 里编辑，下次刷新仍会被删除（原语义）。加一个显式「转为手动」开关，让用户能把 auto 模型显式保住。

**后端**（`app/database.py` `update_provider` UPDATE 分支，L1496-1506）：
- 已存在模型（`m["id"] in existing_ids`）若前端传 `source: "manual"`，则 UPDATE 里同时 `SET source = 'manual'`。
- **不带** source → 保持原样（守住「不翻转」语义，不破坏已验收行为）。
- 新模型 INSERT 仍是 manual（不变）。

```python
# UPDATE 分支（仅当显式传 manual 才翻转）
if m.get("source") == "manual":
    # 在原 UPDATE 里加 SET source = 'manual'
```

**前端**（`app/web/static/app.js` 模型编辑表单）：
- 编辑 auto 模型时，表单出现「转为手动（不会被刷新删除）」checkbox。
- 勾选 → 提交时该模型对象带 `source: "manual"`。
- manual 模型不显示此开关（已手动）。

**验收标准**：
- 编辑 auto 模型不勾选 → source 仍 auto，下次刷新可能被删（原语义）。
- 编辑 auto 模型勾选 → source 变 manual，下次刷新保留。
- manual 模型刷新永不删、不被上游覆盖（已验收，不回归）。

## 5. 验证方案

1. 刷新某 provider → 记录 auto 模型数。
2. 通过 API 手动加一个隐藏模型（source=manual）。
3. 再刷新 → manual 模型**保留**，auto 同步。
4. 删除该 provider → manual + auto 模型全部级联删除。
5. UI 上供应商卡片出现「添加自定义模型」入口，能成功加模型并出现在模型管理页。
6. 老库升级：旧 data.db 跑迁移 → source 列出现，存量行=auto。

## 6. 风险与注意

- **迁移兼容**：老库升级需 ALTER TABLE，注意 WAL / 备份；`_SCHEMA` 与迁移都要覆盖新装 + 升级两条路径。
- **刷新语义变更**：manual 模型永不因刷新删除——需在 UI 明确标注「自定义模型不会随刷新移除」。
- **`_model_from_row` 加 source 键会改变返回 dict 形状**：现有 `test_discovery.py` 等若做精确 dict 相等会比较红，需同步检查。
- **UNIQUE 冲突**：手动加已存在的 auto 模型 id 会被 `INSERT OR IGNORE` 静默吞，UI 应提示「已存在」而非假装成功。
- **测试**：`tests/test_custom_model_source.py` 已覆盖上述全部语义；现有 `test_discovery.py` 需确认 refresh 行为不回归。
